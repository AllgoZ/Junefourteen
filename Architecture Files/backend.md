# JUNEFOURTEEN — Backend Guide

This is the practical, "about to write backend code" companion to
`ARCHITECTURE.md` — Supabase client conventions, the repository/service/
action layering, the full database schema, RLS shapes, migrations, caching,
auth, payments, and the backend-specific gotchas. `ARCHITECTURE.md` stays
the authoritative history/rationale record (see its §14–§22 for the source
material this doc distills, and its §14 specifically for the full narrative
behind every schema decision); when the two disagree, trust
`ARCHITECTURE.md` and fix this file. See `FRONTEND.md` for the UI-side
counterpart — the two together cover "about to write any code in this repo."

## 1. Stack

- **Supabase** — Postgres, Auth (email/password; Phone provider disabled,
  see §7), Row Level Security. No Supabase Storage — images go to
  Cloudinary instead (`lib/cloudinary/`).
- **Hand-written types** (`lib/supabase/types.ts`) — not generated by the
  Supabase CLI (no `supabase login` available in this environment, see §5).
  Keep this file in sync by hand whenever a migration changes a table shape.
- **Razorpay** (`razorpay` npm package) — Checkout + webhook, **live mode**,
  real credentials, real charges (§8).
- **Cloudinary** — image storage/CDN, admin uploads only.
- **`pg`** — direct Postgres connection, migration runner only (§5); the app
  itself never uses `pg` at request time, only the Supabase client libraries.

## 2. The four Supabase clients — pick the right one

| File | Auth | RLS | Use for |
|---|---|---|---|
| `lib/supabase/client.ts` | Browser session (cookies) | Enforced | Client Components only |
| `lib/supabase/server.ts` | Cookie-bound, per-request | Enforced, as the signed-in user (or anon) | Server Components, Server Actions, Route Handlers — the default choice |
| `lib/supabase/admin.ts` | Service-role key | **Bypassed entirely** | Only after the caller is already verified (`requireAdmin()`, or a Server Action that's independently authoritative like order creation) |
| `lib/supabase/anon.ts` | None — no cookies | Enforced, as anonymous | Public, cacheable reads called from inside `unstable_cache` (which forbids request-scoped APIs like `cookies()` in its callback) |

`admin.ts` and (transitively, via `lib/cloudinary/admin.ts`) anything that
imports it are guarded with the `server-only` package — an accidental
import from a Client Component is a **build failure**, not a runtime leak.
See §13 for the taint gotcha this creates.

**Rule of thumb**: reach for `server.ts` by default. Reach for `admin.ts`
only when you've already checked authorization yourself (there is no
admin-role RLS policy anywhere — see §4) or the operation is inherently
public-but-privileged (inserting an order, an order request, or a rate-limit
hit — see §9). Reach for `anon.ts` only inside an `unstable_cache` callback.

## 3. The three-layer pattern

```
lib/repositories/*.ts          raw Supabase queries, customer-facing (RLS'd
                                or explicitly admin-client, per function)
lib/repositories/admin/*.ts    raw Supabase queries, always via the
                                service-role client, always admin-only data
lib/services/*.ts              the fetch boundary for Server Components —
                                wraps a repository call in unstable_cache
                                (tags + revalidate: 3600), or does light
                                orchestration (auth flows, cart merging)
app/**/actions.ts              "use server" Server Actions — the only thing
                                a <form>/client component ever calls
                                directly; requireAdmin()/verifySession()
                                first, then repository/service calls, then
                                revalidateTag/revalidatePath
```

A repository function takes a `SupabaseClient<Database>` as its first
parameter rather than constructing its own — this is what lets the same
query function serve both an RLS-scoped caller and (where appropriate) the
admin client, and is why every repository file is trivially testable/
scriptable standalone (see §13's verification discipline). Concrete shape,
from `lib/repositories/order-requests.ts`:

```ts
export async function listOrderRequestsForUser(
  supabase: SupabaseClient<Database>,
  userId: string
): Promise<OrderRequestRow[]> {
  const { data, error } = await supabase
    .from("order_requests")
    .select("*")
    .eq("user_id", userId)
    .order("created_at", { ascending: false });
  if (error) throw new Error(`listOrderRequestsForUser: ${error.message}`);
  return data;
}
```

Every repository function throws on `error` with the function name
prefixed (`throw new Error(\`fnName: ${error.message}\`)`) rather than
returning a result-union — callers (services/actions) catch at their own
boundary instead of every call site re-checking an `{ data, error }` shape.

`lib/repositories/admin/*.ts` skips the client parameter — every function
there constructs (or is passed) the admin client, since by definition
everything under it only ever runs after `requireAdmin()`.

## 4. Database schema reference

All tables live in `public`, created across `supabase/migrations/0001`–
`0021` (§5). Full column-level detail and the *why* behind non-obvious
choices (join table instead of a single FK, snapshot columns, singleton
tables) is in `ARCHITECTURE.md` §14 — this is the compact map.

**Catalog**
- `products` — the core entity. `is_active` (soft-delete/hide),
  `is_sold_out` (the *only* flag that blocks a purchase — see
  `stock_quantity` below), `custom_size_enabled`, `stock_quantity`/
  `low_stock_threshold` (visibility only, §14 note on 0008),
  `size_chart_image_url`/`_cloudinary_public_id`/`_image_alt` (0020 —
  optional per-product size-chart image).
- `collections` — named groupings, own cover image.
- `product_collections` — many-to-many join (a product can belong to
  several collections — not a single `collection_id` FK).
- `product_images`, `product_sizes`, `product_sleeve_options` — child rows,
  `sort_order`-ordered, cascade-deleted with their product.
- `product_pieces` (0021) — per-piece pricing (Top / Bottom / Dupatta).
  `name`/`price`/`default_selected`/`sort_order`/`is_active`. Zero rows ⇒
  the product uses its single `products.price`. With rows, the storefront
  makes the customer tick ≥1 and `createOrderAction` charges the
  server-computed **sum** (never the client's line price). Same
  public-read RLS shape as `product_images`; admin writes id-preservingly
  via `reconcileProductPieces` so `cart_items.selected_piece_ids` stays
  valid across a product save.

**Customer data**
- `profiles` — one row per `auth.users` row (`id` = `auth.users.id`,
  cascade), auto-created by the `handle_new_user()` trigger on sign-up.
  `role` (`customer`/`admin`) is guarded against self-escalation by the
  `guard_profile_role_change` trigger — only the service-role client can
  change it (§6).
- `addresses`, `wishlist_items` — fully owned by `user_id`.
- `carts`/`cart_items` — one cart per user (`carts.user_id` is `unique`);
  `cart_items` has a partial unique index reproducing the client's
  `buildLineId` merge logic exactly (same product+size+sleeve merges,
  `coalesce`d against `'std'`/`'any'`; custom-measurement and per-piece
  lines never DB-merge — the index's
  `where custom_measurements is null and selected_piece_ids is null`
  clause; `matchesLine` compares the sorted `selected_piece_ids` (0021)
  arrays in app code instead).

**Orders**
- `orders` — `order_number` auto-generated (`JF-<year>-<seq>`,
  `order_number_seq`), `status` and `payment_status` as independent
  enums (an order can be `pending` fulfillment but `paid`), `shipping_
  address`/`billing_address` as `jsonb` snapshots (not a FK to
  `addresses` — an order must survive the customer later editing/
  deleting that address), `razorpay_order_id`/`razorpay_payment_id`
  (0012), `tracking_number`/`tracking_url` (0011), `tax_amount`/
  `coupon_code` (0013).
- `order_items` — `product_id` is `on delete set null`, with `product_
  name`/`product_slug`/`product_image`/`unit_price` all **snapshotted**
  onto the row — an order must render correctly even after the product
  is later edited or deleted. `selected_pieces` (0021) is a text snapshot
  ("Top + Bottom + Dupatta") of a per-piece line; `unit_price` is already
  the server-computed sum.
- `order_requests` (0018/0019) — the "Request to Order" pre-order lead
  capture for sold-out products. **Not** `orders`/`order_items` — a lead,
  not a priced/paid transaction. Same snapshot convention
  (`product_name`/`product_slug`, `product_id` nullable/`set null`).
  `user_id` nullable — a guest's phone number is used to find-or-create
  an account via `linkOrCreateAccountByMobile` (§7) so the request still
  ends up attributed; `status` (`new`/`contacted`/`fulfilled`/
  `cancelled`) is admin-managed.

**Admin-managed site content** (all admin-only writes; public-read where a
storefront section needs it)
- `banners` — homepage hero carousel.
- `social_links` — footer/"Follow Along" destination.
- `shipping_zones` — replaces a formerly-hardcoded rate table; one zone
  flagged `is_default`.
- `coupons` — `discount_type` (`percentage`/`fixed`), `times_used` is
  server-incremented at order time, never client-writable.
- `tax_settings`, `homepage_campaign`, `about_page_content` — **singleton
  tables**: `id boolean primary key default true check (id)`, so a second
  `insert` always collides with the PK. Always `update`, never `insert`,
  after the seed row.
- `homepage_gallery_images` — the 4-tile "Follow Along" grid, a real list
  (not a singleton) despite being a fixed count in the UI today.
- `legal_pages` — `slug` (`'privacy'`/`'terms'`) is the natural key, not a
  singleton — two named rows. `body` uses a tiny, dependency-free
  convention (`## Heading` starts a section, blank lines separate
  paragraphs), parsed by `components/marketing/legal-page-body.tsx`, not a
  markdown library — see `FRONTEND.md` §9.

**Infrastructure**
- `schema_migrations` — migration-runner bookkeeping (§5), not app data.
- `rate_limit_hits` — backs `lib/rate-limit.ts` (§9); short-lived rows,
  opportunistically cleaned up.

Every admin content table above that has "no policies" in its migration
comment follows RLS shape (b) in §6 below — reachable only via the
service-role client. Confirm the exact current shape of any table by
reading its migration file before writing a new query against it rather
than assuming from this summary — this doc distills, `supabase/migrations/`
is the source of truth.

## 5. Migrations

Numbered SQL files in `supabase/migrations/` (`0001`…`0021` today), applied
in filename order by `supabase/scripts/run-migrations.ts`:

```
npx tsx supabase/scripts/run-migrations.ts
```

- Tracks what's already applied in `schema_migrations` — safe to re-run,
  already-applied files are skipped.
- Each file runs inside its own transaction; a failure rolls back just that
  file and stops the run.
- Connects via `SUPABASE_DB_URL` (direct Postgres, not through PostgREST) —
  **`setDefaultResultOrder("ipv4first")`** is set before connecting because
  Supabase's direct-connection host often resolves an IPv6 address this
  network can't route (`ETIMEDOUT`) otherwise; a real, previously-hit
  failure mode, not defensive boilerplate.
- Used instead of the Supabase CLI's `db push` because that needs an
  interactive `supabase login` (browser OAuth) unavailable in this
  environment — a deliberate, documented substitution, not a missing
  feature.

**Writing a new migration**:
1. Next number, short descriptive name (`0020_whatever.sql`).
2. A comment block at the top explaining *why*, not just what — every
   existing migration does this; it's the primary record of intent since
   there's no separate design-doc-per-migration.
3. **Seed admin-editable content with today's exact hardcoded values** when
   converting something from hardcoded to admin-managed (see `0014`,
   `0016`, `0017`) — the goal is that publishing the migration changes
   *nothing* on the live site until an admin actually edits something.
4. Add the matching hand-written types to `lib/supabase/types.ts` — nothing
   generates this automatically.
5. Run the script, then update `ARCHITECTURE.md` §14 if the schema itself
   (not just this doc) needs the new table/column documented.

## 6. RLS conventions — two shapes, pick per table

**Shape (a) — public-read + owner-scoped**, for anything with a genuine
public storefront view and/or a genuine per-customer owner:

```sql
create policy "products_public_read" on public.products
  for select using (is_active = true);

create policy "addresses_owner_all" on public.addresses
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

A child table (images/sizes/cart_items) scopes through its parent via an
`exists (select 1 from parent where parent.id = child.parent_id and
<parent's own condition>)` subquery rather than duplicating the owner
column — see `product_images_public_read`/`cart_items_owner_all` in
`0003_rls.sql`.

**Shape (b) — RLS-enabled-with-zero-policies**, for admin-only content
(`shipping_zones`, `coupons`, `tax_settings`, `homepage_campaign`,
`homepage_gallery_images`, `legal_pages`, `about_page_content`,
`rate_limit_hits`, `schema_migrations`, `order_requests` for its write
path):

```sql
alter table public.shipping_zones enable row level security;
-- no create policy statements — PostgREST default-denies both anon and
-- authenticated roles; only the service-role client (BYPASSRLS) or a
-- direct Postgres connection can reach the table at all.
```

**There are no admin-role write policies anywhere in this codebase** — not
even on tables customers can also read. Every admin write goes through a
Server Action using the service-role client, after `requireAdmin()` has
already run. This is a deliberate "one enforcement mechanism, not two that
could drift apart" choice (documented in `SECURITY.md` §2) — don't add a
`profiles.role = 'admin'`-checking RLS policy as a "belt and suspenders"
measure; it would be redundant with the app-layer check and is a second
place authorization logic could silently diverge from the first.

`orders`/`order_items` are a notable **owner-select-only** variant of shape
(a): customers can read their own rows, but there is deliberately no
insert/update/delete policy for them at all — order creation and status
changes only ever happen through service-role code (`createOrderAction`,
admin actions), never a direct client write, even from the order's own
owner.

## 7. Auth patterns

**Customer (email/password)** — Supabase Auth directly, email confirmation
required. `lib/services/auth.ts#signIn`/`signUp`. Always
`supabase.auth.getUser()` (`lib/auth/dal.ts#verifySession`, memoized with
React's `cache()`), **never `getSession()`** — `getUser()` revalidates the
JWT against Supabase Auth rather than trusting the cookie's embedded claims
unverified. Follow this in any new session-reading code.

**Admin** — no separate Auth mechanism; a `profiles.role = 'admin'` row,
gated in two independent layers:
1. `proxy.ts` (repo root — Next 16 renamed `middleware.ts`) blocks any
   unauthenticated/non-admin request to `/admin/*` (except `/admin/login`)
   before the route renders.
2. `requireAdmin()` (`lib/auth/dal.ts`) as the **first line of every admin
   Server Action** — actions are reachable by direct POST, not just through
   the gated UI, so layer 1 alone doesn't cover them. If you add a new
   admin action, call this first — don't rely on the proxy alone.

There is no public "become an admin" path — `profiles.role` can only be
changed by the service-role client (database-trigger-enforced, §6), and in
practice only via `supabase/scripts/promote-admin.ts`.

**Mobile passwordless** (`lib/services/auth.ts`) — three entry points, all
built on the same mechanism, all sharing the same explicitly-accepted
zero-verification tradeoff (no OTP, either direction — see `SECURITY.md`
§1):
- `signUpWithMobile` — creates a Supabase Auth user with a synthetic,
  never-sent `mobile-<digits>@phone.invalid` email (RFC 2606-reserved,
  guaranteed non-routable) and a random, never-shown `crypto.randomUUID()`
  password, signs in with it immediately, then stores the *real* phone
  number on `profiles.phone` and clears `profiles.email` so the synthetic
  address never surfaces in the UI. Exists because this Supabase project's
  Phone auth provider is disabled — confirmed directly, not assumed — so
  `phone` can never be the Auth identifier; routing through the already-
  enabled Email provider with a synthetic address was the workaround.
- `signInExistingMobileAccount` / `signInOrSignUpWithMobile` — a returning
  customer's number is found by `profiles.phone = X and profiles.email is
  null` (the `email is null` check is a second, independent guard so this
  can never touch a normal email/password account even if some future
  feature also sets `phone`), the account's password is **rotated** via
  the admin API (no old password ever needed) and signed in with fresh.
- `linkOrCreateAccountByMobile` — a **standalone**, non-refactored variant
  of the same two mechanisms above, used only by the "Request to Order"
  guest flow (`submitOrderRequestAction`) to attribute a guest's lead to an
  account without disturbing the mobile-signup-dialog's own code path.
  Fails silently (`return {}`) on any error — linking is a bonus, never a
  reason to block the actual submission.

## 8. Payment integration (Razorpay)

**Live mode, real credentials, real charges** — there is no test-mode
toggle active on this deployment. Two independent, additive confirmation
paths, both required to be correct on their own:

**1. Checkout callback** (client-initiated, immediate) —
`createOrderAction` (`app/(site)/checkout/actions.ts`) computes the order
**authoritatively server-side** (price, shipping, tax, discount all
recomputed fresh from `getProductsForPricing`/`getShippingEstimate`/
`getActiveTaxRate`/`validateCoupon` — the client-supplied cart lines' price
fields are never trusted), creates the Razorpay order
(`lib/payments/razorpay.ts#createRazorpayOrder`), and the client runs
Razorpay Checkout.js. On success, `verifyRazorpayPaymentAction` calls
`verifyRazorpaySignature` — HMAC-SHA256 of `"<order_id>|<payment_id>"` keyed
by `RAZORPAY_KEY_SECRET`, `crypto.timingSafeEqual` (constant-time, not
`===`) — and cross-checks the verified `razorpay_order_id` against the
order row's own stored value before marking it paid.

**2. Webhook reconciliation** (`app/api/webhooks/razorpay/route.ts`) — the
safety net for a tab close/dropped network/JS error between capture and
the client callback. **A separate signature scheme, a separate secret**:
`verifyRazorpayWebhookSignature` HMACs the **raw, unparsed request body**
against `RAZORPAY_WEBHOOK_SECRET` (never `RAZORPAY_KEY_SECRET`) — the route
handler calls `request.text()` first and verifies before any `JSON.parse`
or DB read. Looks the order up by `razorpay_order_id`
(`orders_razorpay_order_id_idx`), and calls the same `markOrderPaid`
**idempotently** — checks `payment_status !== "paid"` first, so a retried
webhook or a race with the client path is a no-op, not a duplicate
transition. Subscribe to `payment.captured` and `order.paid` in the
Razorpay Dashboard's Webhooks page for the `/api/webhooks/razorpay`
endpoint — separately per mode (test/live), since each mode has its own
webhook secret.

**Coupons are re-validated at order-creation time**, not just trusted from
the earlier "Apply" preview — `applyCouponAction` is explicitly
preview-only; `createOrderAction` calls `validateCoupon` again from
scratch, closing the gap where a coupon could expire or hit its usage
limit between preview and purchase.

## 9. Rate limiting

`lib/rate-limit.ts#checkRateLimit(bucket, identifier, { max,
windowSeconds })` — Postgres-backed fixed-window limiter
(`rate_limit_hits` table), chosen over an in-memory counter (no long-lived
process to hold one safely across serverless instances) and over adding an
external service (Postgres is already reachable everywhere via the admin
client). **Fails open** on its own DB errors — infrastructure trouble never
turns into a checkout/sign-in outage.

Current buckets: `sign-in-ip`/`sign-in-account` (`signIn`), `sign-up-ip`
(`signUp`), `order-request` (`submitOrderRequestAction`), plus coupon/order
buckets on the checkout path. `getClientIp()` reads `x-forwarded-for`
(hosting-platform-set; falls back to a single shared `"unknown"` bucket in
local dev, where nothing sets that header — acceptable since only the real
multi-client production case matters here). Adding a new public,
unauthenticated Server Action? Rate-limit it the same way, choosing a
bucket name and `{max, windowSeconds}` proportionate to how abusable a
repeated call would be.

## 10. File upload validation

Every admin image-upload Server Action calls `validateImageFile(file,
buffer)` (`lib/cloudinary/validate-image.ts`) right after the existing
`file instanceof File && file.size > 0` check — three independent gates:
an 8MB ceiling (separate from, and under, the global 10MB Server Action
body cap — a content-specific limit, not the wire-level one), an explicit
MIME allowlist (JPEG/PNG/WebP/GIF), and a **magic-byte signature check
against the actual buffer** — `accept="image/*"` and `file.type` are both
client-supplied hints, trivially spoofable, never the real trust boundary.
Follow this exact sequence for any new image-accepting action rather than
trusting the browser's own file-type gate.

## 11. Server Action conventions

- **`requireAdmin()` (or `verifySession()`/`requireUser()` for a
  customer-scoped action) as the first line**, before touching any input —
  actions are reachable by direct POST, not just through gated UI.
- Mutate via the repository layer (admin client for admin actions), then
  `revalidateTag(tag, "max")` — **the two-argument form is required in this
  Next version** — for anything a cached service function reads, and
  `revalidatePath("/admin/x")` for the admin list page itself.
- Return a plain state object (`{ error? }` or `{ errors: {...} }` +
  `success?`), consumed via `useActionState` — never throw across the
  Server Action boundary into the client for an expected validation
  failure; reserve an uncaught throw for a genuine bug.
- Image-carrying actions: `if (file instanceof File && file.size > 0) {
  validate, upload, delete old if replacing } else { keep existing url }`
  — see `lib/cloudinary/admin.ts` and `saveBannerAction` in
  `app/admin/(protected)/banners/actions.ts` for the canonical shape,
  including the pasted-URL fallback (no Cloudinary `publicId`, never
  passed to `deleteImage`).
- See `FRONTEND.md` §8 for the two form-shell variants (redirect-to-list vs
  stay-on-page) these actions pair with on the client side.

## 13. Backend-specific gotchas

- **`server-only` taints the whole importing file, not just the export you
  use.** A file that imports `lib/supabase/admin.ts` or
  `lib/cloudinary/admin.ts` — even if only one small unrelated export from
  that file is actually consumed elsewhere — fails the build if anything
  downstream tries to reach it from a Client Component. Extract a shared
  constant to its own zero-dependency file rather than fighting this (see
  `lib/config/indian-states.ts`).
- **Verify with a real live query, not just types.** `lib/supabase/
  types.ts` is hand-written and can silently drift from the actual schema
  after a migration. When something backend-related is behaving
  unexpectedly, write a disposable Node/tsx script that calls the real
  Supabase client (or Razorpay API, etc.) directly and inspect the actual
  response — this caught, for example, a genuine `401` credential mismatch
  that a swallowed error had been hiding, and a `phone_provider_disabled`
  error that a design assumption had missed entirely (§7). Prefer this
  over reasoning from types/docs alone whenever the stakes are real.
- **A `server-only`-guarded module can't just be imported into a
  standalone verification script either** — the same taint applies outside
  Next's build too. Inline-replicate the specific logic you need to verify
  (copy the relevant function body into the script) rather than importing
  the real module, when you need to test something `admin.ts`-adjacent
  from outside the app.
- **The direct-Postgres migration host can resolve IPv6-only** on some
  networks (`ETIMEDOUT` connecting) — `run-migrations.ts` already sets
  `setDefaultResultOrder("ipv4first")` for this; if you write another
  script that connects to `SUPABASE_DB_URL` directly via `pg`, carry the
  same line over.
- **The Server Action body size limit is 10MB globally**
  (`next.config.ts`'s `experimental.serverActions.bodySizeLimit`), raised
  from Next's 1MB default because a real camera/phone JPG upload routinely
  exceeds it — raised once, globally, rather than per-route, since every
  image-upload action needs the same headroom.
- **A webhook signature is computed over exact raw bytes** — read the body
  with `request.text()` and verify *before* `JSON.parse`, never
  re-serialize-then-verify; the smallest formatting difference from
  re-stringifying breaks the HMAC.
- **`unstable_cache`'s callback can't use request-scoped APIs** — no
  `cookies()`, no `headers()`. This is exactly why `lib/supabase/anon.ts`
  exists as a fourth client: it needs zero request context to construct.
- **Singleton tables use a `boolean primary key default true check (id)`
  trick**, not a `WHERE id = 1` convention — a second `insert` always
  collides with the existing `true` row. Always `update`, never `insert`,
  once the seed row exists (§4).
